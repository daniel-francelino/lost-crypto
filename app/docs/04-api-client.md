# 04 — API client

One module owns every HTTP call: `lib/shared/api/`. Components and hooks never call `fetch` themselves. Source of truth for shapes: [`api/docs/openapi.json`](../../api/docs/openapi.json) (regenerated by the backend with `make openapi`). **Types may be generated from it** (`openapi-typescript`, a dev dependency decided at scaffolding; record the reason in the commit per CODE-12) but every response is still parsed with zod at the boundary (below).

Base URL: `import.meta.env.VITE_API_BASE_URL` (`http://localhost:8000/api/v1`). Interactive docs of the running API: `http://localhost:8000/docs`.

## The client

```
lib/shared/api/
  client.ts          request<T>(method, path, { query, body, schema, signal })
  api-error.ts       ApiError (status, detail, fieldErrors, kind)
  session.ts         the in-memory access token + refresh single-flight (see 05)
  query-keys.ts      QueryKey registry
lib/<module>/<module>.api.ts     typed verbs per module: listBots(), startBot(id, token?) …
```

`request` does, in this order:

1. Builds the URL from the base, serialises `query` (arrays as repeated keys: `ids=a&ids=b` for `/backtests/compare`).
2. Adds `Authorization: Bearer <access token>` when a session exists. Sends `credentials: "include"` **only** for `/auth/*` (the cookie is scoped to that path anyway).
3. On `401`: refreshes **once** (single-flight: concurrent 401s share one `POST /auth/refresh`), retries the original request once, otherwise clears the session and routes to `/login` (see [05](05-authentication.md#handling-401)). `/auth/login` and `/auth/refresh` themselves are never retried.
4. Parses the body with the call's zod `schema` (`parseOutput`-style) and throws `ApiError` of kind `invalid-response` if it does not match.
5. Passes `AbortSignal` from TanStack Query so a replaced query cancels its request ("an old response never replaces a newer one", UI-1).

Mutations that create a resource are **not** retried automatically; only idempotent GETs are (Query's default retry is lowered to 1 for GET, 0 for mutations).

## Errors

The backend answers `{"detail": ...}` everywhere (FastAPI):

| Status | Body `detail` | Meaning | UI behaviour |
|---|---|---|---|
| 401 | string | missing/expired token, bad credentials, or account temporarily locked (deliberately indistinguishable) | refresh once, else login. Login form shows the generic message |
| 403 | string | role `viewer` tried a write, or the request `Origin` is not in `CORS_ORIGINS` (cookie endpoints) | toast with the message; the control should already have been hidden. An Origin 403 is a deployment bug |
| 404 | string | unknown id / not found | `NotFoundPage` for detail routes |
| 409 | string | conflict (state changed, e.g. bot not stopped, version mismatch) | refetch the resource and tell the user what changed |
| 422 | string **or** array of `{loc, msg, type}` | domain rule (string; this includes the live safeguards: not ready, wrong confirmation name, no approval) or request validation (array) | array → map `loc` to form fields; string → form-level error, shown verbatim in the dialog that caused it |
| 503 | string | auth not configured, or credential vault not configured | full-page "backend not configured" with the message |
| 5xx / network | — | server or connection down | error state with retry; the top bar shows "API offline" |

`ApiError` exposes `status`, `detail`, `fieldErrors: Record<string, string>` (from the 422 array) and `kind: "http" | "network" | "invalid-response"`. Expected failures are shown, never thrown into an error boundary; the boundary is for bugs. Messages shown to the user are **pt-BR copy from a mapping**, not the raw English `detail` (which is kept in the toast's "details" only for the operator and logged with `logError`).

## Money and numbers

The API serialises every decimal as a **string** (`initial_capital`, `equity`, `price`, `quantity`, `fee`, `return_pct`…); a few inputs accept `number | string`. Rules (decision F5):

* Types are `string` in the app. No `Number(...)`, `parseFloat`, `+x` on a money or quantity value; no arithmetic in the frontend. If a derived value is needed (e.g. a delta), ask for it in the API.
* Display through one formatter, `lib/shared/format.ts`: `formatMoney(value, currency)`, `formatQuantity(value, decimals)`, `formatPercent(value)`. They pass the **string** to `Intl.NumberFormat#format` (which accepts decimal strings without rounding through float on current engines — **To verify** on the browsers we support; fall back to a string-based formatter if not).
* Inputs (`FormInputMoney`, `FormInputNumber`) keep the string and send it as a string. Validate with `rules` and a zod regex (`^\d+(\.\d+)?$`), not with `number`.
* Charts need numbers: convert only at the chart boundary in one `toChartRows` helper per chart, and say in a name that the result is for drawing (`equityChartRows`). Chart values are never sent back to the API or shown as exact amounts.
* The quote currency is part of the symbol (`BTC/USDT` → `USDT`); derive it from the symbol, do not hard-code.

## Dates and time

All timestamps are ISO-8601 UTC (`2026-10-31T01:18:01Z`). Candle times (`open_time`, `bar_time`) are UTC bar boundaries; the live daily-loss cap resets at the **UTC** day boundary.

* One module, `lib/shared/dates.ts`, wraps `date-fns` + `@date-fns/tz`; the Date API (`new Date`, `Date.now`, `toLocale*String`, `Intl.DateTimeFormat`) is banned elsewhere by lint. Display goes through `lib/shared/format.ts`.
* Show times in the operator's zone **with the zone visible**, and show **UTC explicitly** for candle/bar times and anything tied to the daily cap (UI-11). A tooltip always offers the other zone.
* Date-only range inputs (backtest, import) are sent as ISO date-times at UTC midnight; the form says "UTC".

## Lists

The growing lists page with `limit` + `offset` and report the size of the whole list in the **`X-Total-Count`** response header (exposed through CORS): `GET /audit-events` (also filters `bot_id`, `event_type`), `GET /bots/{id}/orders`, `GET /bots/{id}/signals`, `GET /backtests`. They are newest first; there is still no server-side sorting or free-text search. Therefore:

* `DataTable` runs in server mode for these (`total` from the header, `page`/`pageSize` → `limit`/`offset`); sorting by column and text search work on the rows of the loaded page only and say so. `request` returns the header alongside the body (`{ data, total }`) for paged calls.
* Short lists (`/bots`, `/exchange-connections`, `/auth/users`, `/market-data/imports`, `/strategies`) are loaded whole and handled on the client.
* `limit` and `offset` are part of the `QueryKey`, and `keepPreviousData` keeps the page on screen while the next one loads.
* A cap such as "latest 500 equity points" (`/bots/{id}/equity`) is stated on the screen.

## Validating responses

`schemas.ts` in each module holds zod schemas named after the API models (`botSchema` for `BotOut`) and the types derive from them (`z.infer`). Reasons: the backend adds fields over time; the app must fail loudly at the boundary, not render `undefined`. Enum-like fields use `z.nativeEnum` over `as const` objects (`BotState`, `ExecutionMode`, `OrderStatus`, `ConnectionStatus`, `JobStatus`, `Timeframe`, `Role`, `Side`) — a value the app does not know becomes a visible "unknown" badge, not a crash.

## Query keys

A registry, never inline arrays (CODE-4):

```ts
export const QueryKey = {
  Auth: { me: () => ["auth", "me"] as const },
  Bots: {
    all: () => ["bots"] as const,
    overview: () => ["bots", "overview"] as const,
    detail: (id: string) => ["bots", "detail", id] as const,
    summary: () => ["bots", "summary"] as const,
    orders: (id: string, limit: number, offset: number) =>
      ["bots", id, "orders", limit, offset] as const,
    signals: (id: string, limit: number, offset: number) =>
      ["bots", id, "signals", limit, offset] as const,
    portfolio: (id: string) => ["bots", id, "portfolio"] as const,
    performance: (id: string) => ["bots", id, "performance"] as const,
    equity: (id: string, limit: number) => ["bots", id, "equity", limit] as const,
    readiness: (id: string) => ["bots", id, "live-readiness"] as const,
  },
  Backtests: { /* list(limit) · detail(id) · trades(id) · equity(id) · compare(ids) · sweep(id) */ },
  MarketData: { /* coverage(symbol, timeframe, exchange) · imports(limit) · candles(params) */ },
  Strategies: { all: () => ["strategies"] as const },
  Exchanges: { connections: () => ["exchange-connections"] as const },
  System: {
    status: () => ["system", "status"] as const,
    capabilities: () => ["system", "capabilities"] as const,
    killSwitch: () => ["system", "kill-switch"] as const,
  },
  Audit: {
    list: (botId: string | null, eventType: string | null, limit: number, offset: number) =>
      ["audit", botId, eventType, limit, offset] as const,
  },
  Users: { all: () => ["users"] as const },
} as const;
```

After a mutation, invalidate by the **prefix** (`QueryKey.Bots.all()`), not by guessing which screens are open.

## Polling (decision F10)

No WebSocket exists. Bots act on candle close (minutes) and the worker writes a heartbeat; seconds-level polling is enough. Use `refetchInterval` on the queries below; Query does not poll in a hidden tab (`refetchIntervalInBackground: false`, keep it), and refetches on window focus.

| Data | Interval | Why |
|---|---|---|
| `GET /system/status` | 5 s | worker heartbeat, kill switch, stale bots: the safety light of the whole app |
| `GET /bots/overview` | 10 s | dashboard cards |
| Bot detail: bot, portfolio, orders, signals | 5 s while on the screen, 2 s right after a start/stop/pause | the observed state follows the desired state asynchronously |
| `GET /bots/{id}/equity`, `/performance` | 30 s | heavier, changes per candle |
| Jobs: `GET /backtests/{id}`, `/market-data/imports/{id}`, `/backtests/sweeps/{id}` | 2 s **until** `status` is `completed` or `failed`, then stop | `POST` answers **202 Accepted**; the work runs in the worker |
| Everything else (strategies, connections, users, coverage, audit) | on demand + on focus | |

The UI states the freshness it shows: a small "updated 3 s ago" tied to `dataUpdatedAt`, and the **stale** treatment (greyed + warning) when `system.worker.alive` is false or the bot's heartbeat is old — a trader must never read frozen numbers as live.

## Asynchronous commands (desired vs observed state)

`start`, `pause`, `stop` and `promote` change the bot's **`desired_state`** and answer 202; the worker later converges **`observed_state`**. The UI shows both: while they differ it shows "starting…/stopping…" and keeps polling fast; it reports success only when `observed_state` matches (or `last_error` explains why not). A toast on "202" alone would lie.
